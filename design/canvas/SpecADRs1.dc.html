spec/adr/001-spec-driven-renderer.md

ADR-001: Spec-driven renderer over generated UI code

Status

Accepted · 2026-11-19 · Deciders: Quilt team (A, B)

Update (Nov 19): the AppSpec is now stored on the app's page block in Supabase (ADR-006), and the spec schema is a Pydantic model whose TypeScript types are generated (ADR-004). The renderer contract is unchanged.

Context

Clair has to turn a sentence into a working app in seconds, live on stage, and the app must keep working the next day. Code generators (Lovable, Bolt, Emergent) can build anything but output varies run to run, needs a build step and breaks in ways a user cannot fix. Quilt's pitch promise is "Clair builds from tested blocks, not generated code". Home also needs every app to emit the same signals (face, pending, dated rows, changes), which only works if every app has the same typed shape.

Decision

We will have Clair write only an AppSpec (JSON, Zod schema in lib/spec.ts) drawn from a closed union of 9 blocks over typed collections. One AppView renderer draws every app; blocks are pure views that read rows and evaluate values, and cannot fetch, run code or style themselves. Invalid specs get one retry with the Zod errors, then a friendly error.

Consequences

Positive

  • Builds are fast and deterministic to render; a spec that parses always draws.
  • Home, search filters, stitches and the calendar of everything work for any app, because fields and dates are typed.
  • Specs export cleanly (the marketplace format later) and can be diffed for History and undo.

Negative

  • Needs that don't fit 9 blocks can't be built; the demo must pick apps that fit.
  • Every new capability is a schema change plus a component, not a prompt tweak.

Neutral

  • The same renderer serves the Build preview, so preview and result never differ.

Model choice

Prompting a general model (Claude Opus 5.5) with structured output; building or fine-tuning was ruled out by time. Coupled to it: the system prompt and the Zod schema. Reversal cost is low because the schema, not the model, is the contract; any model that fills the schema works. Reopen if more than 1 in 10 build prompts in the test set need a retry.

Alternatives considered

  • Generated React per app: unlimited range, but slow, fragile and unsafe to run live. Rejected.
  • Spec plus escape-hatch custom code blocks: reintroduces the fragility for a minority of apps. Deferred until the block library shows a real ceiling.

References

spec/ui-tech-plan.md sections 2–3; pitch doc "Technical quirks and risks".

spec/adr/002-mock-api-route-handlers.md

ADR-002: Mock API as Next route handlers over an in-memory store

Status

Superseded by ADR-004 and ADR-008 · 2026-11-19. The API is FastAPI on Vercel over Supabase; fixtures survive only as Clair's recorded "sample" runs.

Originally: Proposed · 2026-11-19 · Deciders: Quilt team (A, B)

Context

The UI must run against a backend on day one, before Clair or a database is ready, and the demo's key moment is the same data updating live on a phone and a laptop. The pitch doc names Postgres or SQLite with one table. A database server, migrations and hosted credentials cost hours we do not have.

Decision

We will implement the API as Next.js route handlers backed by lib/db.ts, an in-memory store (specs, rows, proposals, change log) seeded from fixtures, running in one long-running Node process on Railway. Clair sits behind one module with two adapters, fixture and live (Claude), chosen per call kind: photo parse is live by default (the judged feature), the rest default to fixture, and every fixture result is visibly marked "sample". The store lives on globalThis so Next never makes a second copy; reset and live calls need a demo key. Devices sync by polling GET /api/changes?since= every second.

Consequences

Positive

  • Real HTTP, real shared state: the two-device moment can be tested on the day's third hour.
  • Fixtures make every flow work with zero AI calls while the live photo path is built; a failed live call offers the marked sample instead of hiding the failure.
  • db.ts has a small interface, so SQLite can replace the map later without touching callers.

Negative

  • State is lost on restart (acceptable: we reseed with POST /api/dev/reset before each run).
  • Cannot run on serverless hosting; one process (replicas 1) is a hard limit, and no redeploys during the demo window.
  • Polling adds up to a second of lag on the second device.

Neutral

  • Server-Sent Events can replace polling later behind the same /api/changes data.

Alternatives considered

  • MSW in the browser: fast to set up but each device has its own mock state, so the phone and laptop cannot share an update. Rejected.
  • SQLite or Postgres now: right for beta; setup and hosting time is not worth it for one day.
  • Vercel + KV store: works, but adds a service and keys for no demo gain.

References

spec/ui-tech-plan.md sections 1, 5, 9.

spec/adr/003-basted-proposals.md

ADR-003: Clair writes through basted proposals; the UI animates optimistically

Status

Accepted · 2026-11-19 · Deciders: Quilt team (A, B)

Update (Nov 19): a proposal is stored as a change set with status basted (the same change_sets and events tables every user gesture uses, spec/backend.md); Clair creates it only through its propose_changes tool (ADR-007).

Context

Product principle 3: Clair proposes, you approve; nothing big changes without a visible preview and undo. The design makes this visible as stitch states (basted = waiting for OK, running stitch = saved) and one focal motion, the thread pull on confirm. The pull must start on tap, not after a server round trip, and Home must show exact before/after numbers ("$412 → $376") before anything is saved.

Decision

We will route every Clair write through a Proposal holding row operations. The server, not Clair, expands stitches, computes target apps and face deltas by dry run, and stores inverses on apply so undo is exact. User edits inside an app write directly with an undo toast. On confirm the client animates immediately using the precomputed deltas, sends confirm in parallel, and reverses the animation if the request fails.

Consequences

Positive

  • One card style and one confirm flow serve receipts, captures, check-ins, insights and shares.
  • Thread targets and numbers are always true to the data, whatever Clair claimed.
  • Undo is a single endpoint and a single reverse animation.

Negative

  • A rare failed confirm shows threads then retracts them; acceptable and honest.
  • Proposals must be re-expanded after every Review items edit.

Neutral

  • Other devices see results through the change log as "just changed" tags, never the pull.

Alternatives considered

  • Write first, then offer undo: faster to build, breaks "nothing saves before OK". Rejected.
  • Wait for the server, then animate: simpler failure handling, but adds a visible pause before the signature motion.

References

spec/ui-tech-plan.md section 4; .impeccable/surfaces/app.md (stitch states, signature motion).

spec/adr/004-python-backend-on-vercel.md

ADR-004: Python (FastAPI) backend on Vercel

Status

Accepted · 2026-11-19 · Deciders: Quilt team · Supersedes ADR-002 · Reverses TabOS v3 ADR-6 (Go, agent in-process)

Context

TabOS v3 puts the command service and the agent loop in one Go monolith and rejects a separate Python agent service: a second runtime, tool types defined twice. Its own reversal trigger is "a Python-native agent team". That is us: the team writes Python, Anthropic's Python SDK has a tool runner, and the build is one day. The pitch needs one public URL for the laptop and an API the Android app can call without holding the Claude key.

Decision

The whole backend is one FastAPI app on Vercel (Python functions): the command service, the Python formula engine, sync, auth helpers and Clair's agent loop. It reads and writes Supabase Postgres with psycopg through the Supabase pooler so a change set is one real transaction. The one Anthropic key lives only in Vercel's environment. Types cross to the React app as Pydantic models → OpenAPI → openapi-typescript, generated, never hand-copied.

Consequences

  • One runtime for API and agent, as v3 wanted; the language is Python instead of Go.
  • Request-scoped functions: nothing can wait for the user between requests. Clair's menu questions therefore end the request and resume on the answer (ADR-007).
  • Cold starts and the function duration limit apply to every agent run. Check maxDuration and SSE streaming for Python functions on our plan at T1; warm the functions before the pitch.
  • No in-memory shared state; all state is in Supabase, which also removes ADR-002's single-process limit.
  • Reversal trigger: agent runs regularly exceeding the function time limit, or a need for long-lived connections; then move the same FastAPI app to a container host.

Alternatives considered

  • Go per v3: matches the long-term doc; a new language and toolchain for a one-day build.
  • TypeScript (Node): shares Zod schemas with the client; not the team's choice of agent stack.
  • Supabase Edge Functions: no extra host, but Deno and tighter run limits for agent loops.

References

spec/backend.md, spec/clair-agent.md, TabOS v3 §9.4.

spec/adr/005-react-capacitor-client.md

ADR-005: React (DOM) with Capacitor, Android first

Status

Accepted · 2026-11-19 · Deciders: Quilt team · Reverses TabOS v3 ADR-5 (Expo / React Native)

Context

TabOS v3 picks Expo mobile-first with react-native-web and rejects a web-first app. Quilt's whole look and motion already exist as DOM prototypes: CSS tokens, WAAPI, a critically damped spring, an SVG thread pull. Rebuilding them in React Native before the demo is not possible. The demo needs an installed-feeling phone app plus the same app on a laptop.

Decision

One React app built with Vite. Capacitor wraps it as an Android app (APK, sideloaded for DevDay); the same build is served as a website for the laptop and any browser. Native needs go through Capacitor plugins: Camera, speech recognition, text-to-speech, App (deep links, later). The app holds no secrets; it calls our API (ADR-004).
