Consequences

  • The prototype code ports as-is; the design book is the reference implementation.
  • iOS is a later Capacitor target (needs a Mac and signing); share-into-Quilt and push arrive with native targets.
  • WebView quirks replace React Native quirks: test touch, safe areas and the keyboard on the real Android phone at D3.
  • v3's own reversal path already allowed a native-web renderer; blocks over the wire keep the backend unchanged either way.
  • Reversal trigger: WebView performance or native feel measurably hurting retention; then a React Native renderer reads the same API.

Alternatives considered

  • Expo per v3: better native feel and a local SQLite store; every animation rebuilt first.
  • Web only (PWA): fastest, but no Android share sheet, weaker camera and speech access.

References

spec/ui-tech-plan.md §1, TabOS v3 §12.

spec/adr/006-supabase-blocks-table.md

ADR-006: Supabase Postgres with the v3 blocks table, layout kept whole

Status

Accepted · 2026-11-19 · Deciders: Quilt team · Adapts TabOS v3 ADR-3 and §3.1; defers v3 ADR-1 (encryption)

Context

Apps are made by Clair at run time, so there is no fixed table per app. v3 stores everything as blocks in one table: every record is its own block under its collection, which gives per-record order, versioning, undo and sync. The earlier plan (ADR-002) kept each app as one JSON spec plus a rows map in memory. We also need accounts, live updates between devices and file storage, with no time to run those ourselves.

Decision

Supabase: Postgres, anonymous auth that can later link Google or email, Realtime and Storage. One blocks table in v3's shape (workspace_id, parent_id, position, block_type, collection_id, properties jsonb, version, deleted_at). App (page), collection and record blocks are real blocks. For DevDay the app's layout stays one AppSpec JSON on the page block instead of a tree of layout blocks. Properties are plain JSONB protected by row-level security on workspace_id; v3's envelope encryption and query index are deferred.

Consequences

  • Records get per-record order, versions, soft delete and undo now; splitting the layout into child blocks later does not touch records.
  • No encryption at rest beyond Supabase's own; the settings screen must not claim more.
  • Queries filter JSONB directly; fine at personal scale, revisit with the v3 query index if a collection passes ~10k records.
  • Reversal trigger: per-block sharing or encryption becomes a requirement.

Alternatives considered

  • Full v3 block tree now: most faithful; the renderer and Clair's spec compiler get much bigger.
  • Spec document + rows table: simplest; diverges from v3's invariant and needs a migration later.
  • Railway Postgres: we would build auth, pairing and live updates ourselves.

References

spec/backend.md §2, TabOS v3 §3, §7.

spec/adr/007-clair-agent-loop.md

ADR-007: One Clair agent loop on the Anthropic SDK tool runner

Status

Accepted · 2026-11-19 · Deciders: Quilt team · Replaces the "structured call per request" design in ui-tech-plan.md §4; cuts down TabOS v3 §9.3

Context

Clair must handle any input (words, voice, a live photo of a fridge or a schedule, a screenshot, a PDF), work out what it is, read Sam's apps, ask when unsure and propose changes across apps. A single structured call can only see what we pack into it and cannot ask a question. Anthropic's agent guidance: start simple, give actions their own tools when the harness must gate, show or audit them (Claude Code shows question-asking as a tool that blocks the loop), keep a stable cached prefix and an append-only history.

Decision

Every input goes through one loop built on the Anthropic Python SDK tool runner (@beta_tool, client.beta.messages.tool_runner), model claude-opus-5-5, with our own typed tools: perceive (report_understanding), read (list_apps, get_app, query_records, search_records, get_usuals, get_faces, get_notes), ask (ask_user), remember (save_note) and propose (propose_changes, propose_app). Clair never writes app data: propose_changes only creates a basted change set (ADR-003). Because a Vercel request cannot wait for the user, ask_user ends the request and the answer resumes the saved, unchanged transcript. A context snapshot (apps, lists, open items, usuals, notes) is packed into each turn so most inputs need one or two model turns; there is no separate fast path for receipts.

Consequences

  • One code path to build, test and evaluate; any photo works, not only receipts.
  • A receipt costs about as much as the old one-shot call because the snapshot is pre-packed; a fridge needs two or three turns.
  • Pause and resume rely on restarting the runner from saved messages; confirm at the T1 spike, otherwise use a short manual loop with the same tools.
  • Stage latency depends on the model; "Use sample" and recorded fixture runs are the fallback.

Alternatives considered

  • Claude Managed Agents: Anthropic runs the loop and keeps sessions, and a question waits natively; beta, a container per session, user data held in sessions, less predictable stage latency.
  • Claude Agent SDK: the Claude Code harness, built for coding agents with file and shell tools; needs the CLI process, a poor fit for Vercel functions.
  • Pydantic AI, LangGraph: another layer over what the SDK already does, with no gain for this tool set.
  • Structured call for receipts plus an agent for the rest: two paths to build and test.

References

spec/clair-agent.md, TabOS v3 §9.3–9.4.

spec/adr/008-online-writes-read-cache.md

ADR-008: Online writes with a local read cache

Status

Accepted · 2026-11-19 · Deciders: Quilt team · Defers TabOS v3 §5 (offline-first sync) and ADR-4 (WASM formulas)

Context

v3 is local-first: a durable op queue on every device, device-suffixed positions, conflict events and a formula engine compiled to WASM so totals update offline. That is weeks of work. For DevDay the need is narrower: screens must open instantly, the laptop must update within a couple of seconds of a confirm on the phone, and every number must be right.

Decision

Writes go to the server and only succeed online. Each device keeps a read cache in IndexedDB (blocks, faces, last_server_seq) per workspace, paints from it at once, then catches up with GET /sync?since=seq. Supabase Realtime on the events table tells devices when to catch up. Simple gestures (tick, swipe, reorder) update the screen at once and roll back if the server rejects them; Clair confirms wait for the server. All formulas and faces are computed in Python on the server and returned with every change.

Consequences

  • Fast opens and live two-device updates with little code; nothing is lost because nothing is queued.
  • No offline editing: without a connection the app is read-only and says so.
  • Totals change after the server answers (a few hundred milliseconds), not instantly on device.
  • The cache is per workspace and cleared on sign-out and on a schema version change, so a shared device never shows another person's data.
  • Reversal trigger: users editing offline (class, subway) or formula lag noticed in testing; then add v3's op queue and a client evaluator.

Alternatives considered

  • v3 offline-first now: right long term, far too large for the event.
  • No cache, always fetch: simplest, but every open waits on the network and a cold Vercel function.

References

spec/backend.md §6–7, TabOS v3 §5, §6, §11.
